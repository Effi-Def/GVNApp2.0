## Item di base (fondazionali)

### [000] Separazione Visibilità vs Partecipazione Evento (P0)
- **Status:** done
- **Tipo/Area/Effort:** refactor | core | L

- **Progress (groundwork):**
  - Stato: implementazione completata lato codice; smoke test manuale eseguito ✅
  - Tipi aggiornati: `visibility` / `participation` (backward-compatible)
  - Service layer: lettura `participation` + dual-write in `updateParticipation()` (mantiene anche `participants[]` e `participantIds`)
  - Presence per-giorno: bloccata se non hai RSVP `yes` (niente creazioni implicite)
  - Chat: accesso solo dopo RSVP `yes` (UI + rules)
  - Regole Firestore: lettura evento anche via `visibility` (`public` / `restricted.users`)
  - Verifica: `npm run build` OK

- **Obiettivo:**
  - Separare in modo esplicito:
    - **Chi può vedere un evento** (visibilità)
    - **Chi e come partecipa** (partecipazione)

- **Decisioni UX:**
  - Un evento visibile tramite Fattoria:
    - appare in lista eventi e calendario
    - NON crea automaticamente una partecipazione
    - stato iniziale implicito: "irrisolto"

- **Dominio (modello dati evento - bozza):**
  - Nota: questa è una bozza di riferimento. Va tradotta poi nei tipi reali in `src/types` e nei servizi Firestore.

  visibility:
    - type: public | restricted
    - farms: FarmId[]
    - users: UserId[]

  participation:
    - [userId]:
        - status: yes | maybe | no | left
        - role: owner | member
        - accessLevel: full | readonly | none

- **Regole partecipazione:**
  - La partecipazione viene creata solo su interazione (es. clic RSVP).
  - `status = no` => `accessLevel = readonly`
  - `status = left` o ban => `accessLevel = none`

- **File coinvolti:**
  - `src/types/*` (event model)
  - `src/services/firestore.ts` (eventService)
  - `firestore.rules`

- **Acceptance criteria:**
  - [x] Evento visibile senza creare partecipazione (via `visibility.type` + `visibility.users`; “farms” arriva con [001])
  - [x] Partecipazione creata solo su interazione (RSVP)
  - [x] Nessuna logica implicita visibility => participation

- **Test plan:**
  - [x] `npm run build`
  - [x] Utente in fattoria vede evento, ma non risulta partecipante finché non clicca RSVP
  - [x] Utente con status=no vede evento in readonly (grigio) e non può scrivere

## Feature principali

### [001] Fattorie (Maiali) + Visibilità eventi (P1)
- **Status:** in-progress
- **Tipo/Area/Effort:** feature | groups | L

- **Obiettivo:**
  - Introdurre le **Fattorie** come gruppi tematici.
  - Ogni utente può appartenere a più fattorie.
  - Il creatore dell’evento (**Re Maiale**) sceglie la visibilità:
    - Pubblico
    - Solo Fattorie selezionate
    - Fattorie + Maiali invitati (one-shot)

- **Creazione fattoria:**
  - Chiunque può creare fattorie (nessun limite iniziale).
  - Nota futura: introdurre piano a pagamento per “più di X fattorie”.

- **Membership fattorie (decisione):**
  - Meccanismo: **link/codice di invito** che genera una **richiesta pendente** (non ingresso automatico).
  - Il Re Maiale approva/nega.
  - Nessuna directory globale utenti.

- **Dominio / Ruoli:**
  - **Owner = Re Maiale**
    - gestisce fattoria, membri, eventi, richieste di ingresso
  - **Member = Maiale**
    - può creare spese/liste/sondaggi se `accessLevel = full`
  - Visibilità evento ≠ partecipazione evento (vedi [000]).

- **Uscita/ban:**
  - Uscita/ban da fattoria:
    - perde visibilità degli eventi passati: Sì
    - può vedere spese/sondaggi creati in passato: No

- **UX / Copy:**
  - Pagina dedicata “Fattorie”
  - Creazione fattoria: nome (es. “Fattoria di ...”)
  - Invito: bottone “Invita maiali” => copia link
  - Richieste pendenti visibili solo al Re Maiale
  - Badge evento: `Pubblico` / `Riservato`
  - Mostrare solo nomi delle Fattorie e/o conteggi, mai elenco membri (privacy)

- **Punti aperti (da definire):**
  - [ ] UI e regole per evento multi-fattoria (filtri, badge, notifiche)
  - [ ] Trasferimento ownership in caso di ban dell’Owner (vedi “Decisioni finali”)

- **Acceptance criteria:**
  - [x] Creazione fattoria libera
  - [x] Ingresso solo previa approvazione Re Maiale (richiesta pendente)
  - [x] Nessuna lista globale utenti
  - [x] Evento riservato visibile solo se matcha `visibility` (fattorie e/o utenti one-shot)
  - [x] Member con `status=no` => evento grigio/readonly solo per quel member
  - [x] Member può creare spese/liste/sondaggi solo con `accessLevel=full`

- **Test plan:**
  - [ ] Join via link => richiesta pendente (manuale, 2 account)
  - [ ] Approva => utente NON vede eventi con `date` < `joinedAt` (policy “nuovi membri”) (manuale)
  - [ ] Decline partecipazione => readonly per quel member (manuale)

## Decisioni Finali (confermate)

### 1) Richieste di ingresso in Fattoria
- Meccanismo: link di invito
- Stato: richiesta pendente
- Scadenza: la richiesta decade se il link viene rigenerato (opzione “rigenera link”)
- Nessuna scadenza temporale automatica

### 2) Visibilità eventi per nuovi membri
- Un maiale che entra vede solo gli eventi futuri
- Eventi passati: non visibili
- Eventi senza data ma creati prima dell’ingresso: non visibili

### 3) Creazione della partecipazione a un evento
- La partecipazione viene creata solo quando il maiale clicca:
  - Partecipo / Forse / Non partecipo
- Non creano partecipazione:
  - apertura del dettaglio evento (solo descrizione/info generali)
  - lettura passiva
  - visualizzazione calendario
- La chat evento diventa accessibile solo dopo “Partecipo” (status=yes)

### 4) Notifiche ed engagement
- Evento nuovo nella Fattoria: notifica inviata anche ai non partecipanti
- Stato iniziale evento per il maiale: “irrisolto”
- Nessuna notifica successiva finché non interagisce

### 5) Ban e ownership
- Quando un maiale viene bannato dalla Fattoria:
  - perde accesso a tutti gli eventi e contenuti della Fattoria
  - ownership degli eventi creati viene trasferita (Re Maiale o sistema) (TBD: definire regola precisa)
  - storico preservato

### 6) Naming e dominio
- Entità principali: Fattoria / Maiali
- Nessun alias “Gruppo” in UI
- Naming ispirato a La fattoria degli animali mantenuto come riferimento concettuale
